# Gateway 0.1.17 release notes

## Original-file attachment delivery

Gateway can assess attachments for a selected session and deliver supported
files as their original bytes, preserving each filename and its association
with the human message. The per-file delivery limit is 25,000,000 bytes,
inclusive. A post containing an over-limit file is refused as a whole with
HTTP 413 and the `attachment_over_limit` error code. Existing inline image
handling is unchanged.

## Decision briefings on upgrade

Organizations that learned decision briefings in 0.1.16 keep their configured
owner and route automatically. The rail-scoping migration moves the learned
rule into substrate rules so it continues to observe requests from all agents.
An existing substrate rule takes precedence and is never overwritten.

## Harklight lifecycle commands

`tightbeam harklight-revise`, `harklight-retract` and `harklight-settle` no
longer refuse a message Tightbeam has no send record for. Give them what
Harklight needs and they pass the operation through; Harklight still decides
who may change a message, and Tightbeam adds no permission check of its own.

- `harklight-revise` and `harklight-retract` take an optional
  `--session <handle>`, the Harklight session the message was sent in.
- `harklight-settle` takes an optional `--op-id <key>`, the Harklight operation
  to retry.
- With no send record these commands change no wake or subscription state, and
  the result says so (`wakeEffect: "none"`, `subscriptionEffect: "none"` and a
  note beginning "no subscription effect"). Without the flag they refuse and
  name it. With a send record, behavior is unchanged, and a flag that
  contradicts the record is refused.

A superseding `harklight-send` that names a send whose outcome is unknown no
longer fails as a whole. The valid targets are superseded; the unresolved one is
reported as an unchanged target with a reason, like the targets Harklight
itself warns about. A supersede whose only target is the unresolved send is
still refused until that send is settled.

## Harklight Agent compatibility

Tightbeam 0.1.16 and later works with Harklight Agent v0.1.14 and v0.1.15.
Every send passes `--type`, and no removed flags are used.

## Breaking changes

The dispatch API changes are:

- A successful `post` response adds `result.outcome`, `result.sessionKey`,
  `result.deviceId`, `result.clientMessageId`, `result.messageId`, and
  `result.turnSeq` for both text and attachment posts. `outcome` is
  `recorded` for an appended or queued post and `duplicate` for an idempotent
  retry. A duplicate returns the existing canonical message ID and does not
  create a second message. `turnSeq` is `null` until a turn is assigned and a
  safe integer when one is available. Existing `ack` and `dedupe` fields
  remain available.
- Known post refusals now use HTTP 409 instead of a successful response with
  only a legacy dedupe result. A client-message identity reused with different
  content returns `error.code` `client_message_conflict`; a skipped delivery
  returns `error.code` `not_deliverable`. These responses contain no success
  `result` or legacy `dedupe` field. Retryable server failures continue to
  return an error response when persistence is unknown.
- A `post` can include canonical attachment references. Gateway validates
  those assets at send time and records each attachment's delivery result in
  message history.
- A session CLI credential cannot invoke the human `post` path through
  `/agent/dispatch`. The Chat service's org-authenticated human send remains
  supported; `post` is not an advertised agent verb.
- The `assess_attachments` dispatch verb reports the selected `sessionKey`,
  `clientMessageId`, `maxDeliverableAttachmentBytes`, and one ordered
  assessment per asset. Each assessment is `will-deliver`,
  `will-not-deliver`, or `unknown`, with a reason for non-delivery or
  uncertainty. The exact per-file delivery limit is 25,000,000 bytes.
- Attachment history adds a `delivery` object with `pending`, `delivered`,
  `not-delivered`, or `unknown` outcome and an applicable reason. When a
  delivery result is committed, Gateway publishes the
  `message.attachment_delivery.updated` notice with its canonical message,
  session, client-message, and asset identifiers.
- `harklight-revise`, `harklight-retract` and `harklight-settle` results can
  now carry `subscriptionEffect` and `note` fields when Tightbeam has no send
  record for the message. A superseding `harklight-send` result can list a
  superseded target with `effect: "unchanged"` and a `reason` for a send whose
  outcome is unknown; that case was previously a refusal of the whole send.
