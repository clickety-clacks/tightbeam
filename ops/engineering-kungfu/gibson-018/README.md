Source inspection establishes the following limits:

- Each `identity edit` commits and publishes one file, then reloads archetypes. It does
  not refresh existing sessions or reload rule files. Publish dependencies before
  references and verify intermediate composed identities as well as the final tree.
- A successful `identity relearn`, or `learn` of an already learned bundle, reloads
  archetypes, rails and rules without refreshing sessions or creating execution lanes.
  This supplies a law reload, not the missing rule-file edit operation. A gateway
  restart is not inherently required to reload law.
- `identity apply` and tuning enter a session execution lane. Even
  `ensure_lane_quiet` creates a lane whose initialization nudges pending work.
  They are not general no-turn operations.
- A harness change also calls `Spinup.ensure_ready`, which may need an inference
  wiring probe. It starts a fresh engine context while preserving the Tightbeam
  session, workdir and work graph. Private engine reasoning does not carry over.
- Same-harness tuning is designed to preserve the conversation, but still uses the
  execution-lane boundary and must respect held or queued work.

## Custody on an installed system with no reparent command

Reuse healthy delivery orchestrators whose existing scope fits. Where none exists,
staff the smallest required delivery role when turns are permitted. Each delivery
orchestrator opens the assignments it must supervise, including independent review.
POs keep spirit decisions and transfer delivery work through explicit acceptance.

For an existing worker, preserve its assignment until a successor owner has accepted
the useful output, remaining work, constraints and any independent review links.
Open the replacement from the actual delivery owner using the same work item, and
record the predecessor link in its brief and attests. Version 0.1.8 has no
`--succeeds` option. Do not create competing implementation holders or revoke a
producer whose review still depends on its identity.

Where custody cannot safely move, keep it in place and arrange an explicit routing
agreement for material events. The old opener still receives substrate-generated
notifications. Label this an interim routing repair, not repaired ancestry. Transfer
new work first and let historical edges remain truthful. Creating a new org merely
to redraw old edges would lose the point of preserving ongoing work.
