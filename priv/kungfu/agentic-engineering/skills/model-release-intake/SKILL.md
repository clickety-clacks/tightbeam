# Model policy intake

Use the shared preferred-models guidance for selection and fallback. Reconsider its
working set when observed capability, model retirement, cost or access changes the
organization's useful choices. A catalog arrival is information, not a requirement
to adopt every advertised model or retune every session.

Verify exact model IDs, supported efforts, permitted families and host/harness routes.
Distinguish advertised capability from runnable credentials and observed quality.
Keep uncertainty explicit. Describe a new model once in the shared capsules, then
place it in applicable activity rows by the work it can perform. Availability order
need not be a monotonic ladder of intelligence or price; each candidate must satisfy
the activity's capability floor.

Reconcile affected archetype defaults and preference metadata with the activity
policy. Keep mixed and single-family views consistent. Do not silently change an
alias, substitute an unavailable successor or leave defaults pointing only at a
retired model. Existing model/harness changes require supported tuning and preservation
of useful context and custody; a policy edit alone does not retarget running agents.

When available in an authorized development environment, `mix tightbeam.catalog.diff`
compares the live catalog to shared working-set capsules. Missing selected models cause
a nonzero result; new unselected arrivals are informational. A zero result does not
prove credits, task fitness or model-policy quality. Do not assume a runtime intake
steward, notification or gate exists merely because this diagnostic exists.

Record the consequential policy change, evidence, affected activities and actual
application state. Use proportionate evaluation where capability is uncertain. Keep
separable work moving while a genuine model-access decision is resolved.
